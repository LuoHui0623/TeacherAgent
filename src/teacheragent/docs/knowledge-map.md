# 知识地图设计

> **性质**：知识地图域设计说明。定义「有源抽取」方向、核心对象（`KnowledgePoint` / `KnowledgeEdge`）、大纲契约的重设计需求、累积逻辑与数据演进策略。
> 业务口径见 `PRD.md`「知识地图」，Agent 模型见 `docs/agents.md`。

## 一、方向：有源抽取 + 拓扑

**结论**：知识地图走**有源抽取**，不做头脑风暴生成。

理由：头脑风暴生成是**无源**的 —— 让 LLM 在一个没有 ground truth 的空间里自由发明节点和边，生成质量没有参照物可校验，不稳定是必然的，调提示词救不回来。

PRD 原文要求的本来就不是生成：

> **知识图谱构建**：Agent 从教材与笔记中**抽取**知识点与关系，**人工可修正**
> **学习路径规划**：**基于图谱拓扑**推荐先修序列

两个关键词：**抽取**（有源）、**拓扑**（有结构）。

## 二、三种结构，不能混

现有大纲契约把三种结构塞在同一个实体里，这是字段混乱的根因：

| 结构 | 节点 | 边 | 来源 | 可信度 |
|---|---|---|---|---|
| **章节树** | 章节 / 大纲条目 | 父子、顺序 | 人工撰写 + 人工审批 | 确定 |
| **知识点图** | 知识点 | 先修、关联、包含 | 从源抽取 + 人工确认 | 取决于抽取质量 |
| **挂载关系** | — | 章节 → 知识点 | 大纲编写时标注 | 介于两者之间 |

三者粒度不同、生命周期不同、可信度也不同。把它们混在一个实体里，会导致「哪些字段是权威、哪些是派生」永远说不清。

## 三、现有大纲契约的问题（不可直接当确定来源）

> 逐条分析与字段取舍建议见 **`docs/outline-contract.md`**（独立讨论稿）。本节只列问题清单。

以 `frontend/services/content-pipeline/contracts.ts` 的 `CourseBlueprintPayload` / `OutlineItemPayload` 为例：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **三种结构混装** | 见第二节 |
| 2 | **知识点实体缺失** | 只有 `knowledgePointIds: string[]`，知识点本身没有任何契约定义（本文件第四节补齐） |
| 3 | **层级表示重复** | `parentId` 与 `children` 同时表达父子关系，两者可以漂移 |
| 4 | **排序表示重复** | `order` 与数组顺序同时表达次序 |
| 5 | **两种依赖轴语义不清** | `prerequisites` 与 `dependsOnItemIds` 都表示「依赖」，但前者像知识点、后者像条目 |
| 6 | **聚合字段可推导** | `CourseBlueprint.estimatedMinutes` 可由条目求和；`expectedOutcomes` 与 `LearningBrief` 重复 |
| 7 | **命名不成族** | `CourseBlueprint` 与 `OutlineItem` 两个词指同一棵树 |
| 8 | **字段含义不明** | `requiredArtifacts`、`depth` 的取值域与用途没有定义 |

**结论**：这些字段需要严谨重设计，**不能直接当确定去使用**。顺序是**先定字段、再定名字**。

## 四、核心对象与关系

> 契约实现：`frontend/services/knowledge-map/`（`types.ts` 类型、`model.ts` 归一化与校验），测试见 `frontend/tests/knowledge-map-model.test.ts`。

### 4.1 依赖顺序：先有 Domain，后有 KnowledgePoint

```text
Domain 词表          ← 先定义 / 分配
      ↓ 只允许引用词表内的项
KnowledgePoint       ← 后创建 / 抽取
      ↓ 通过带类型的边互连
KnowledgeEdge
```

**为什么 Domain 必须在前面**：如果知识点可以自由写领域，领域会随每次抽取不断分化出近义写法（「机器学习」「ML」「机器学习/深度学习」），最后没人说得清体系里到底有几个领域。先把词表定下来，知识点只能**从词表里选**，领域体系才是收敛的。

**抽取时的处理**：遇到词表里没有的领域，**不直接写进知识点**，而是产出**候选 Domain**，经人工确认入词表后，才能挂到知识点上。这与「只提取不推断」是同一个精神 —— 抽取不能凭空造领域。

### 4.2 Domain（领域）

`Domain` 是**受控词表条目**，不是知识点。

| 字段 | 必填 | 说明 |
|---|---|---|
| `path` | 是 | 领域路径，唯一。如 `编程语言/Python`。**前缀即祖先**。 |
| `label` | 否 | 展示名。缺省时取路径最后一段。 |
| `description` | 否 | 说明。 |
| `source` | 否 | 来源：人工定义 / 从教材分配 / 抽取后人工确认。 |

**路径形态**：`前端/框架/React` 让「扁平」成为路径的特例 —— 只写一级就是扁平设计；要表达「前端 ⊃ React」时用**前缀匹配**即得包含关系，**不需要给领域再建一棵树，也不需要迁移数据**。

**祖先可以是隐式的**：词表里可以只登记 `编程语言/Python`，此时 `编程语言` 作为**隐式分组**存在（过滤与分组时用到）。也可以显式登记 `编程语言` —— 好处是能给它单独配展示名与说明。

> **注意**：KnowledgePoint 上「只写最具体路径」的规则，**不适用于词表本身**。词表允许父子并存。

**语义引用而非 id 引用的代价**：`KnowledgePoint.domains` 存的是路径字符串。领域改名需要批量更新引用 —— 这是为可读性付的代价。兜底是 `validateGraph` 会把「引用了词表里不存在的领域」直接报出来，不会静默断链。

### 4.3 KnowledgePoint（知识点）

知识点是**内容实体**：可以被说「我掌握了 / 我没掌握」的最小单元。

**必填字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 稳定标识（slug，如 `python.decorator`），**分配后不随 `label` / `domains` 变更**。可读、可 diff、可被笔记与教材锚点手写引用。 |
| `label` | string | 展示文本。可自由修改；改名不改变 `id`。 |
| `domains` | string[] | 领域，**多值**，**只能引用 Domain 词表内的 `path`**。**只写最具体的路径**（祖先被后代蕴含即删除），按字典序排序。 |

**可选字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `aliases` | string[] | 别名与同义写法。**归并的唯一依据**：「装饰器」与「Python 装饰器」靠它识别为同一条。 |
| `summary` | string | 一句话说明。用于节点悬浮与无障碍文本。 |
| `sources` | KnowledgeSource[] | 来源记录（教材 / 笔记 / 抽取批次），支撑「这条知识点为什么存在」。 |

**多值领域的冗余来源与解法**（两条规则即可消除）：

| 冗余 | 例子 | 规则 |
|---|---|---|
| **祖先被后代蕴含** | `["编程语言", "编程语言/Python"]` | **只写最具体的路径**，前者删除 |
| **顺序差异** | `["机器学习", "编程语言/Python"]` 与反序 | **按字典序排序**，同一份数据只有一种写法 |
| **排序口径** | — | 用**码位序**（确定性的），不用 `localeCompare` —— 契约需跨环境一致，不能依赖运行时的 ICU / 语言设置 |

前缀匹配必须**按分隔符**做，不能用裸 `startsWith` —— 否则「编程语言」会被误判为「编程语言工具」的祖先。过滤时命中自身与后代：过滤 `编程语言` 会带上 `编程语言/Python`。

**刻意不放在知识点上的字段**

| 不放什么 | 放哪里 | 理由 |
|---|---|---|
| 学习者状态（已完成 / 学习中 / 未开始） | 独立映射 `{ knowledgePointId, status, evidence }` | 那是**用户态**，会随时间变化；放进内容实体会让「知识点」变成「某个人的知识点」 |
| 父子关系 | `KnowledgeEdge` | 关系统一为边，不在实体上长字段（见 4.4） |
| 领域定义 | `Domain` 词表 | 领域要先定义，知识点只引用（见 4.1） |

### 4.4 KnowledgeEdge（知识点关系）

| 字段 | 类型 | 说明 |
|---|---|---|
| `from` / `to` | string | 知识点 `id` |
| `type` | enum | `contains` / `prerequisite` / `related` |
| `sources` | KnowledgeSource[] | 可选，来源记录 |

| 类型 | 含义 | 方向约定 |
|---|---|---|
| `contains` | 包含：上位概念由下位概念构成 | `from` = 上位，`to` = 下位 |
| `prerequisite` | 先修：要学 `to`，先得学 `from` | `from` = 先修的 |
| `related` | 关联：无方向 | 存储时按 `id` 排序去重，避免出现反向重复边 |

**为什么父子做成边而不是字段**：父子、先修、关联在结构上一致、语义不同。做成边后**一张图只有一种节点 + 一种边**，投影、布局、遍历、渲染全部统一；否则实体上会长出 `parentIds` / `prerequisiteIds` / `relatedIds` 三个字段，每加一种关系就要改一次实体。

### 4.5 四条边界规则

1. **Domain 必须先定义。** 知识点只能引用词表内的领域；抽到新领域要先进词表（人工确认），再挂知识点。
2. **`domains` 不是知识点的父节点。** 否则「机器学习」会同时以领域和知识点的身份出现两次，归并逻辑必然崩。`domains` 回答「属于哪个领域」（过滤与分组），`contains` 边回答「由哪些更小知识点构成」（结构与聚合），两者可以重合但**不互相推导**。
3. **层级只表达一次。** `contains` 已经表达包含关系，实体上就不再设 `parentId`。
4. **知识点与章节是两种节点。** 章节在章节树里，知识点在知识点图里，二者通过**挂载关系**连接 —— 挂载属于大纲契约，不属于知识点契约。

### 4.6 示例

```jsonc
{
  "domains": [
    { "path": "编程语言" },
    { "path": "编程语言/Python", "label": "Python" },
    { "path": "数学/优化" },
    { "path": "机器学习" }
  ],
  "knowledgePoints": [
    { "id": "python", "label": "Python", "domains": ["编程语言/Python"],
      "summary": "通用编程语言" },
    { "id": "python.closure", "label": "闭包", "domains": ["编程语言/Python"] },
    { "id": "python.decorator", "label": "装饰器", "domains": ["编程语言/Python"],
      "aliases": ["Python 装饰器", "decorator"],
      "sources": [{ "kind": "outline", "ref": "content-pipeline/…" }] },
    { "id": "ml.gradient-descent", "label": "梯度下降",
      "domains": ["数学/优化", "机器学习"] }
  ],
  "edges": [
    { "from": "python", "to": "python.decorator", "type": "contains" },
    { "from": "python.closure", "to": "python.decorator", "type": "prerequisite" }
  ]
}
```

### 4.7 外部关系

| 外部对象 | 关系 | 归属 |
|---|---|---|
| 章节树 | 挂载：章节 → 知识点 | 大纲契约（T12） |
| 学习者 | 状态映射：知识点 → 已完成 / 学习中 / 未开始 | 独立映射，挂知识点 `id` |
| 画像 | 「已学内容 / 薄弱点」将来与知识点对齐 | 独立映射，不改知识点实体 |

### 4.8 已知不足

1. **别名与「不同知识点」的界线**：工具只能提示，最终靠人工。这条界线决定图谱会不会被近义节点淹没。
2. **多值领域对归并的影响**：两个知识点 `domains` 不同并不代表它们是不同知识点 —— 归并依据是 `aliases`，不是 `domains`；领域差异只能作为人工裁决的提示信号。
3. **领域改名的连锁影响**：路径是语义引用，改名需批量更新知识点。校验能发现断链，但不能自动修复。
## 五、领域词表的来源与判别规则

### 5.1 场景推演：从笔记目录看领域

用户的笔记树（`E:\笔记`，样本不大但结构真实）：

```text
笔记/
├── 生活/
│   └── 狗狗 · 想法 · 一起看/电影 · 游戏攻略/MC
├── IT之路/
│   ├── 【机器学习】 · 【深度学习】 · 【prompt】/模型适配提示词
│   ├── 编程语言/
│   │   ├── 前端
│   │   ├── C++【英雄编程】/ 标准库 · C++学习
│   │   ├── GO
│   │   └── Python/ 标准库 · 第三方库 · Python教程
│   ├── 操作系统/ shell语言
│   ├── 环境配置/ 系统环境 · 项目环境配置/包管理 · 项目管理
│   ├── 计算机科学 · 经验实现 · 小工具 · skill/腾讯skillhub
│   ├── STUDY/项目课/假如我要写Agents · 知乎
│   └── Vibe Coding
└── Xmind笔记/
    ├── 人工智能/ 崔老师 · 梁勇/md图片 · 算法 · 西瓜书
    ├── 总结图片/ markdown/markdown图片
    └── python入门/ 可视化
```

**类比**：一个知识点 ≈ 一篇整理好的 markdown 笔记，domain ≈ 笔记所在的目录。类比基本成立，但样本暴露出六条必须处理的规律。

### 5.2 六条规律

| # | 规律 | 样本证据 | 对设计的约束 |
|---|---|---|---|
| 1 | **层级深度可变** | `操作系统` 1 层、`Python` 3 层、`Python/标准库` 4 层 | 不能假设固定层级；**路径形态（可变深度）是正确选择** |
| 2 | **同层级混着不同分类轴** | `IT之路` 下并列学科（机器学习）、语言（Python）、活动（STUDY）、来源（C++【英雄编程】） | 词表需要**判别规则**，不能照抄目录 |
| 3 | **同一领域存在多个路径** | `前端` 同时在 `编程语言/前端` 与 `技术栈/前端` | 这正是要归并的对象；也说明**目录不是权威体系** |
| 4 | **命名带装饰、语言混用** | `【机器学习】`、`C++【英雄编程】`、`STUDY`、`skill`、`Vibe Coding` | 词表需要**命名规范**（去装饰、统一大小写与语言） |
| 5 | **材料、活动、附件与领域混在一棵树里** | `Python教程`、`C++学习`、`STUDY`、`md图片` | 这些**不是 domain**，见 5.3 |
| 6 | **领域之间既有嵌套也有交叉** | 人工智能 ⊃ 机器学习 ⊃ 深度学习；机器学习 × Python；CSS × 前端 | 嵌套用路径，**交叉用多值** |

### 5.3 判别规则：什么算 domain

> **能装下「多个可独立学习的东西」，且本身是名词性主题的，才是 domain。**

两把尺子，缺一不可：

| 尺子 | 通过 | 不通过 |
|---|---|---|
| **粒度** | 能归集多个可学单元（`Python` 下能装装饰器、生成器、标准库） | 本身就是一个可学单元（「装饰器」是知识点） |
| **性质** | 名词性主题（学科 / 技术 / 子技术） | 材料、活动、来源、附件 |

按这个规则给目录里的实际节点归类：

| 目录里的东西 | 是 domain 吗 | 应该是什么 |
|---|---|---|
| 机器学习、Python、CSS、操作系统 | ✅ | domain |
| 教程、某本书、某门课（`Python教程`、`西瓜书`） | ❌ | **source** / 教材 |
| 作者、课程品牌（`崔老师`、`英雄编程`） | ❌ | **source** |
| 活动（`STUDY`、练习、总结） | ❌ | 学习行为，不是领域 |
| 附件与产物（`md图片`、`总结图片`） | ❌ | 资产，不是领域 |
| 「技术栈」这类**视角** | ⚠️ | 它不是领域，是**同一批领域的另一种分组** |

最后一行是样本里最值得注意的：`技术栈` 与 `编程语言` 并列在顶层，但两者不是一类东西 —— 前者是**视角**，后者是**分类轴**。**顶层 domain 应当是互斥的分类轴**，否则过滤与分组会互相打架。

### 5.4 词表怎么来：分配 + 人工裁决

回到「先定义好或**分配**好 domain」：

```text
已有材料（笔记目录 / 教材大纲 / 抽取结果）
      ↓ 分配候选
候选 Domain 列表
      ↓ 按 5.3 判别 + 5.2 归并 + 命名规范
人工裁决
      ↓
正式 Domain 词表
```

- **分配可以自动化**：目录路径、教材的领域标签都可作为候选来源。
- **裁决必须人工**：去材料、去活动、去来源、合并重复路径、统一命名。
- 这与抽取知识点时的「候选 → 人工确认 → 入库」是**同一条流水线**，只是对象是领域。

> **关键提醒**：目录树是**个人的资料组织方式**，领域词表是**知识的分类体系**。两者部分重合但不相等 —— 照抄目录会把 `Python教程`、`md图片` 这类东西带进领域体系。

### 5.5 样本给出的候选词表（裁决前）

```text
编程语言
├── Python
├── C++
├── Go
└── CSS        ← 归属有争议，见下
前端
└── CSS        ← 与上一处冲突，需裁决
操作系统
人工智能
├── 机器学习
└── 深度学习
数学
└── 优化       ← 「梯度下降」跨数学与机器学习，是多值的典型
```

**CSS 是这套规则下最典型的交叉案例**：它既是编程语言（有语法与规范），又是前端技术的组成部分。两条路径都不算错 —— 这正是 `domains` 需要多值的原因。但两条路径**不能靠目录照抄产生**，必须由词表先定义好，再让知识点引用。
## 六、领域演化与版本隔离

### 6.1 问题的本质：不是「关联变了」，而是「归属粒度需要细化」

例：一开始只有 `前端` / `后端`，后来 `后端` 拆成多个编程语言。

这里发生了**两件事**，必须分开：

| 阶段 | 动作 | 需要判断吗 | 可否自动化 |
|---|---|---|---|
| **结构拆分** | 词表里新增 `后端/编程语言/Java` 等节点 | 不需要 | ✅ 可批量 |
| **归属细化** | 把挂 `后端` 的知识点重新挂到更细路径 | **需要** | ❌ 逐条处理 |

**结构拆分不动任何知识点** —— 词表允许父子并存（4.2 已定），加子领域是纯增量操作。真正需要处理的是第二件事。

### 6.2 中间态允许存在，但只在演化过程中

用 dev / prod 类比做**版本隔离**：

| 状态 | 中间态（粗归属、废弃引用） | 用途 |
|---|---|---|
| **工作版本**（working） | **允许** | 演进、试验、分批推进 |
| **发布版本**（published） | **不允许** | 被消费方读取，必须自洽 |

**为什么必须隔离**：如果中间态可以被消费，消费方每次查询都要处理「这条挂的是粗归属」「这条引用已废弃」—— 边界情况会渗透到每一个消费点。版本隔离把这些复杂情况**关在演化阶段**，消费方拿到的永远是干净的图。

### 6.3 推论：合法性是「环境相关」的

**同一份数据，在工作态合法，在发布态非法。**

| 检查 | 工作态 | 发布态 |
|---|---|---|
| 结构合法（`validateVocabulary` / `validateGraph`） | 必须通过 | 必须通过 |
| 粗归属（`findUnrefinedPoints` 非空） | **允许** | **阻塞** |
| 废弃引用（`findDeprecatedPoints` 非空） | **允许** | **阻塞** |

因此职责重新划分：

- `validateGraph` 只回答「**结构**是否合法」—— 与状态无关。
- **发布门禁单独定义**（`collectPublishBlockers`）—— 它才检查中间态。

> **修正上一版口径**：之前写的「校验管合法，清单管待办」只适用于**工作态**；发布态两者都管。

### 6.4 发布门禁

发布（promote）是一次**显式操作**，带门禁：

```text
工作版本 ──[ 门禁 ]──► 发布版本
```

| 门禁 | 检查 | 不通过时 |
|---|---|---|
| 词表合法 | `validateVocabulary` | 阻塞 |
| 结构合法 | `validateGraph(graph, { vocabulary })` | 阻塞 |
| 无粗归属 | `findUnrefinedPoints(...) === []` | 阻塞，**列出待细化清单** |
| 无废弃引用 | `findDeprecatedPoints(...) === []` | 阻塞，**列出待迁移清单** |

门禁不通过时必须给出**可执行的清单**，而不是一句「发布失败」—— 否则用户不知道该改什么。

### 6.5 一个容易踩的坑：确实无法归入子领域的知识点

拆分后，有些知识点可能**真的不属于任何子领域** —— 比如 `HTTP 协议` 挂在 `后端` 下，而 `后端` 已拆成 `编程语言` / `数据库` / `中间件`。

发布态不允许粗归属，所以必须做个决定。**推荐做法：补一个显式的通用子领域**（如 `后端/通用`），而不是让它们继续挂在父级。

这不是逃生舱 —— 它把「这个知识点不属于任何具体子领域」这个**真实判断**显式记录下来，而不是靠父级挂靠隐式表达。

### 6.6 迁移历史

版本隔离要求**明确的迁移历史**，它有两个用途：

| 用途 | 说明 |
|---|---|
| **可撤销** | 批量重归属一次改 N 条记录，必须能回退 |
| **可追溯** | 发布时冻结「自上次发布以来发生了什么」，成为发布版本的变更说明 |

```ts
interface DomainMigration {
  kind: 'refine' | 'merge' | 'rename';
  from: string[];              // 涉及的原领域路径
  to: string;                  // 迁往的领域路径
  knowledgePointIds: string[]; // 受影响的知识点
  at: string;                  // 发生时间
  by?: string;
  reversedAt?: string;         // 撤销时间
}
```

**发布 = 冻结「词表 + 图 + 自上次发布以来的迁移历史」** —— 于是每个发布版本天然带一份变更说明。

### 6.7 操作形式：批量重归属，而不是逐条编辑

不要让人一条条去改知识点的 `domains` 字段：

```text
选中「后端」下的 N 条知识点（待细化清单）
  → 指定新归属（可多选，如 后端/编程语言/Java）
  → 预览 diff（哪条从什么变成什么）
  → 应用（写入一条 DomainMigration，可撤销）
```

### 6.8 合并与改名：废弃而非删除

直接删掉一个领域会让引用它的知识点断链。所以 `Domain` 用两个字段：

| 字段 | 取值 | 作用 |
|---|---|---|
| `status` | `active` / `deprecated` | 废弃的领域不再出现在选择器里，但**工作态的老引用仍然合法** |
| `replacedBy` | path（可选） | 合并 / 改名的去向，用于一键重归属 |

**改名 = 废弃 + 新建 + `replacedBy`**，与合并同构，不需要单独一套机制。

> **发布态的口径**：发布态**保留 `deprecated` 条目，但保证零引用**。保留是为了让历史可读（能看到「前端」是从「Web前端」合并来的）；零引用由发布门禁保证。

### 6.9 副产品：三张可运营的清单

| 清单 | 定义 | 用途 | 发布态 |
|---|---|---|---|
| **待细化** | 挂在非叶子领域上的知识点 | 拆分后的增量迁移 | 必须清空 |
| **待迁移** | 引用了 `deprecated` 领域的知识点 | 合并 / 改名后的迁移 | 必须清空 |
| **待确认** | 候选领域 / 候选知识点（未入词表 / 未确认） | 分配与抽取的入口 | 必须清空 |

这三张清单把「体系演化」从隐性工程问题，变成用户看得见的运营任务；而**发布门禁就是它们的验收点**。

### 6.10 契约影响

| 对象 | 变化 |
|---|---|
| `Domain` | `status`、`replacedBy?` |
| 门禁 | 新增 `collectPublishBlockers(graph, vocabulary)` / `canPublish(...)` |
| 清单 | `findUnrefinedPoints` / `findDeprecatedPoints` 由「待办提示」升格为**发布门禁** |
| 历史 | 新增 `DomainMigration`；发布冻结「词表 + 图 + 迁移历史」 |
## 七、版本管理

> **状态**：已收敛（讨论定稿，代码待落地）。

### 7.1 两级状态

```text
        编辑（agent / user，行为统一）
                  ↓
        ┌──────────────────┐
        │  暂存（pending）   │  ← 未提交的改动
        └──────────────────┘
                  ↓ 显式 commit（不 commit 就不成版本）
        ┌──────────────────┐
        │ 提交历史（单分支）  │  ← 增量 diff，不可变
        └──────────────────┘
```

**只有两级。** 不引入 git 的「工作区 / 暂存区 / 提交」三级 —— 单用户场景下多一层 index 是多余的一步。上一版图里的「工作区」已去掉，它不是一个独立状态。

### 7.2 编辑与提交

| 要点 | 内容 |
|---|---|
| **来源统一，不因 role 区分** | agent 与 user **走同一套动作**。agent 的输出不是「直接写进图」，而是与用户操作同构的编辑，同样要经暂存才能提交 —— 天然获得人工 review。**暂存区就是「人工可修正」的落点。** |
| **不 commit 不成版本** | 编辑只进暂存；显式 commit 才把暂存内容固化为一个版本。 |
| **暂存的最小提交单位** | **按知识点分条** —— 可以只提交其中一部分。agent 一次可能产出大量候选，用户往往只想采纳其中几条。 |
| **单分支** | 不做分支，只有一条主线；保留「提交有父」的结构以备将来。 |

### 7.3 提交说明

| 来源 | 要求 |
|---|---|
| **agent** | **自动生成**，内容 = **版本变动策略 + 实际变动效果** |
| **user** | **必须由用户填写** |

agent 的说明分两段，因为**意图与实际可能不一致**：

```text
策略：把「后端」下的知识点细化到「编程语言 / 数据库 / 中间件」
效果：迁移 12 个知识点（→ 编程语言/Java 8 条，→ 数据库 4 条；3 条被用户取消）
```

策略是「打算做什么」，效果是「最后成了什么」。两者都记，才知道一次变更的计划与结果。

### 7.4 提交与发布：两个不同的动作

**commit 与 publish 被明确区分：**

| 动作 | 含义 | 谁可以做 |
|---|---|---|
| **commit** | 创建版本（记录一次变更） | **agent 或 user**（行为统一） |
| **publish** | 质量决策：宣告某个提交可作为消费源 | **只能由人同意** |

这条边界正好落在两条**正交**的维度上：

| 维度 | 取值 | 对应动作 | 主体 |
|---|---|---|---|
| **版本维度** | 暂存 / 已提交 | commit | agent 或 user |
| **质量维度** | 中间态 / 干净 | publish（过发布门禁） | **只能人** |

**推论一**：agent 可以创建版本，但**不能宣告「这是发布版」**。
**推论二**：**中间态可以被 commit** —— 提交只记录一次变更，不承诺质量；工作态允许中间态（第六节），提交里当然也可以有。发布门禁作用在**某个提交的快照**上，不是作用在暂存区上。

发布记录只含 `commitId` + `at`，**不另写说明** —— 说明就是本次发布**包含的提交说明**。

**发布记录保留历史列表**（不是只留「当前发布指针」），以支撑「这份教材基于哪个版本的知识图」的溯源。

### 7.5 增量 diff

- 提交存**增量 diff**，不存全量快照。
- **diff 以知识点为单位**（新增 / 修改 / 删除）；**知识点的内部变动也触发 diff** —— `label`、`domains` 等任何字段变化，都算这个知识点的一次变更。
- 撤销 = **revert 产生反向新提交**，不删除历史。

### 7.6 重放与性能兜底

因为存的是增量 diff，要读出「第 N 个版本时的图」，必须**从头把所有 diff 依次应用一遍** —— 这就是**重放（replay）**。

历史长到一定程度后，每次读旧版本都要重放几百次，会变慢。**兜底**指的是：每隔若干次提交额外存一份**全量快照（checkpoint）**，重放时从最近的 checkpoint 开始，而不是从第一个提交开始。git 自己也在做类似的事（packfile、commit-graph）。

**决定：保留设计位，并预设间隔为每 10 次提交。** 逻辑上现在不必真正生成 checkpoint（知识点数据量小，重放几百次也在毫秒级），但：

### 7.7 冲突与并发：用「基线」而不是「锁」

真实的工作方式是**串行**：agent 与 user 通常不会同时工作 —— user 一般只会小改，并且会等 agent 改完再动。所以冲突是**例外**，不是常态。

设计目标应当是：**常态零成本，例外可发现。**

| 方案 | 复杂度 | 问题 |
|---|---|---|
| A. 只做冲突警告 | 最低 | 检测不出「agent 基于过期状态产出」这类隐式冲突 |
| B. 引入「占用 / 锁定」状态 | **高**：要处理超时、强制解锁、agent 崩溃后的恢复 | agent 卡住会把用户一起锁死 |
| **C. 给每条暂存改动记「基线」（推荐）** | 低：只多一个 commit id | 无，检测是确定性的 |

**推荐 C，不引入状态机。** 每条暂存改动记录它**基于哪个提交**产生；应用时若基线 ≠ 当前 HEAD，且与已有改动重叠，就**警告**（不阻塞）。

- **常态**（串行工作）：基线总是当前 HEAD，零打扰。
- **例外**：agent 跑完后 user 又提交了改动 → agent 的条目基线过期 → 明确警告，由人决定怎么处理。

另外建议在界面上**显示 agent 是否正在运行**（可见性），但**不阻止**用户编辑。可见性解决的是「忘了 agent 在跑」，而锁的复杂度不值得 —— 尤其是单用户场景下，被自己的 agent 锁死是最糟的失败模式。

### 7.8 对已有代码的影响（定稿后再处理）

| 已有实现 | 影响 |
|---|---|
| `DomainMigration` 类型 | 降级为「一类提交的视图」，不再是独立实体 |
| `collectPublishBlockers(graph, vocabulary)` | 输入从「图 + 词表」变为「提交快照」 |

**这正是「先讨论、后编码」的例证**：这两处在上一版口径下写成，方向一变就要跟着改。定稿前**不再扩展**。

### 7.9 可调参数的落点（约定）

像「checkpoint 每 10 次提交」这类**可调参数**不应散落在实现代码里，应当：

1. **集中管理** —— 放到所属领域的 config 里；
2. **附功能注释** —— 说明它控制什么、改动会影响什么；
3. 便于**发现问题时及时修改**。

落点：`<领域>/config.ts`（如 `services/knowledge-map/config.ts`）。

```ts
/** 每多少次提交额外存一次全量快照（checkpoint）。调小会变快但存储变多。 */
export const CHECKPOINT_INTERVAL = 10;
```

**为什么不放全项目一个 config**：跨领域混在一起会变成大杂烩，改一处要翻半天，边界也说不清。**领域级集中**既满足「不散落」，又不失边界。

## 八、累积逻辑

知识地图不是一次成型，而是随教材与笔记**累积**。累积要解决的核心是**归并**：

```text
抽取  →  归并  →  人工确认  →  入库
```

- **归并是难点**：「装饰器」与「Python 装饰器」是同一个知识点吗？「Transformer」与「Attention 机制」是父子还是并列？归并的依据就是 `aliases`，但界线靠人工。
- **可复用画像的模式**：画像的「技术栈是累积条目、可整合、整合只做归并不丢信息」是同一类问题，可借用同一套原则。
- **人工确认是质量闸门**：PRD 明写「人工可修正」。抽取结果未经确认不得入库。
- **来源可溯**：知识点与边都记 `sources`，支撑「这条边为什么存在」。

## 九、数据演进：先展示，后消费

| 阶段 | 内容 | 边界 |
|---|---|---|
| **一（当前）** | 把知识地图整理成**展示内容** | 展示内容**仍来自真实数据**，不是 mock；不参与任何决策 |
| **二（后置）** | 推进为**消费能力**：路径推荐、学习者定位 | 是否推进由业务端判断 |

「展示」不等于「假数据」。真实数据反而更省事 —— 源已经在大纲里，写 mock 才是额外工作量。而且展示本身就是价值：大纲确认后立刻能看到结构，是教材生产线的可视化延伸。

## 十、暂不引入 Neo4j

第一期不做多跳遍历与跨域语义关联，查询形态是**局部子图 + 拓扑排序**，数据源在 SQLite，递归 CTE 完全够用。

引入 Neo4j 的代价是：多一个数据库、多一套驱动池、多一份运维负担 —— 换一个本期用不上的能力。**暂不引入。**

> 附注：`pyproject.toml` 的 `neo4j` 依赖与 `infrastructure/store/connection.py` 的 Neo4j 驱动池目前**没有任何消费方**。是否一并移除属独立决定（见 `Task.md` 第五节）。

## 十一、是否需要 Agent

取决于「源」的形态：

| 源 | 提取方式 | 需要 LLM / role 吗 |
|---|---|---|
| 已验证的结构化大纲 | **纯投影**（确定性代码：读大纲 → 构图 → 布局） | 不需要 |
| 教材正文 / 笔记（自由文本） | **抽取** | 需要：一个 role + 一条带人工确认的固定流程 |

**不建议做成自主 agent**：PRD 要求「人工可修正」，「抽取 → 人工确认 → 入库」天然是一条**固定流程**，不是让模型自由决定调什么工具。按 `docs/agents.md` 的模型：

- 它是 **capability**（如 `knowledge-extraction`：教材正文 / 笔记 → 知识点与关系）
- 它有一条 **workflow** 串起「抽取 → 归并 → 人工确认 → 入库」
- 它需要一个 **role**（因为要配模型与温度）

第一期如果只做「从结构化大纲投影」，则**三者都不需要** —— 那是一段确定性代码。
