# 对话与运行发起

> **性质**：对话域设计说明。定义对话消息的存储、一轮 Tutor 对话的写入点，以及 run 的发起面。
> 业务口径见 `Task.md`「六、已确认口径」1、2、7；运行与产物见 `Task.md` 具体设计 A/B/D。

## 一、一份事实：消息只追加

对话是一串只追加的事实，每条消息一行 `chat_messages`：

| 列 | 含义 |
|---|---|
| `message_id` | 消息身份，形如 `msg-<n>`，在同一条对话里递增 |
| `role` | 对话方：`user` / `assistant` |
| `type` | 消息类别：`chat`（普通对话）/ `proposal`（发起一次教材生产的提议） |
| `content` | 正文 |
| `event_time` | 这条消息发生的时刻，与 `node_runs` / `node_artifacts` 同一口径 |

`role` 与 `type` 各管一件事：前者是对话方，后者是类别。词表封闭在 `constants/chat.py`，写接口只接受词表内的取值，因此库里的取值集合可枚举。

`llm_runs` 记录每次模型调用的输入输出与用量，不承载对话；「模型说了什么」只在上表里，两者的关系是「一次调用」与「一条发言」，不互相替代。

只个人使用，不引入 `user_key`；将来要多用户时字段名用 `user_id` 并与 `user_profiles` 对齐。

## 二、写入点

| 写入 | 触发 | 写什么 |
|---|---|---|
| 一轮对话 | `POST /chat/turns` | 先写用户消息，模型回复到位后写 assistant 消息 |
| 用户主动记一条 | `POST /chat/messages` | 一条消息，`type` 由调用方给 |

一轮对话的模型输入由后端组装：读回整段对话，再拼上这一句用户发言。因此「Tutor 看得见历史」不是前端的责任，前端只发这一轮的新发言。

模型调用失败时，已经写下的用户消息保留 —— 那次发言确实发生了，缺的只是回复；重试就是再发生一轮。消息表只追加，不做删除，所以失败不会留下需要清理的半成品。

## 三、发起面

run 由对话中的 `proposal` 发起（口径 1），入口是 `POST /workflows/{workflow_id}/runs`：

1. 认这条消息：必须存在，且 `type` 是 `proposal`；否则 404 / 400。
2. 分配 run id（`run-<n>`，在该流程内递增）。
3. 冻结图快照，并把这条消息作为入口节点捕获的事件写下。
4. 推进到跑不动为止，返回 `runId` 与这一轮推进结果。

run 与消息的关联落在 `node_runs.trigger_message_id`：一个 run 的所有节点行都带同一个消息 id，所以「哪条 proposal 触发了这次运行」不需要额外的表，也不需要 join 对话表。

`proposal` 只是消息类别，不是 Learning Brief 的替代：pipeline 内的 `brief-approval` 保留，图定义不因发起面而改动。

## 四、前端接线

- 学习区 Tutor 抽屉直接渲染 `GET /chat/messages` 的结果，顺序由后端给，前端不排序、不编号。
- 发送走 `POST /chat/turns`；失败时保留输入框内容（用户消息已经落库，重试即可）。
- 「发起教材生产」把输入框这一句写成 `proposal` 消息，再由它创建运行，成功后切到教材生产线 —— 运行历史里最近一次运行就是刚发起的那次。

## 五、当前边界

- 没有流式输出：一轮对话在模型返回后一次写入。
- 没有会话分组：全部消息是同一条对话，按时间排序。
- 没有删除与编辑：消息只追加（口径 7）。
- 发起只认 `proposal`；run 的其它控制动作（暂停 / 继续 / 重跑 / 决断）不属于发起面。
