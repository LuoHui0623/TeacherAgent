# 桌面软件化（讨论稿）

> **状态**：讨论中，**不落代码**。
> **触发**：希望把项目做成桌面软件。
> **冲突提示**：`PRD.md` 现在写着「产品形态：本地优先的 **Web 应用**」，但非目标只写了「不做移动端原生应用」—— 桌面软件是**新的产品形态**，PRD 需要相应更新。

## 一、现状

| 部分 | 形态 | 能否直接装进桌面壳 |
|---|---|---|
| 前端 | React + Vite，产出**静态产物**（`npm run build` → `dist/`） | ✅ 零改动 |
| 后端 | Python + FastAPI（uvicorn） | ❌ 需要进程管理 |
| 启动 | `scripts/dev.py` 起两个进程（后端 8000 / 前端 5173） | 开发期够用，不是产品形态 |

## 二、真正的难点不是「选哪个壳」

容易把注意力放在 Tauri / Electron 的对比上，但这个项目的**难点在 Python 侧**：

1. **进程生命周期** —— 壳要拉起后端、健康检查、崩溃重启、退出时清理（避免僵尸进程）；
2. **端口分配** —— 不能硬编码 8000，要动态取空闲端口并通知前端；
3. **数据目录** —— 安装后没有仓库目录，数据必须写系统标准位置；
4. **Python 运行时** —— 只在**分发给别人**时才成为问题（见第六节）。

**结论：壳只做三件事 —— 开窗口、装前端、拉起后端。** 所有原生能力（文件、SQLite、LLM 调用）都能经 Python 后端暴露，因此**壳不需要丰富的原生能力** —— 选型权重应当偏向「轻」与「少踩坑」，而不是「原生功能多」。

## 三、壳的选型

前提：**壳只做三件事 —— 开窗口、装前端、拉起后端**。所有原生能力（文件、SQLite、LLM）都能经 Python 后端暴露。但既然要求**壳层扩展性强**（将来加原生能力时不被壳挡住），候选如下。

### 3.1 「扩展性强」的四种含义（先分清）

| 含义 | 最强的选项 |
|---|---|
| **能加多少原生能力**（托盘 / 全局快捷键 / 文件监听 / 通知……） | Electron、PySide6 |
| **插件生态有多厚** | Electron、Tauri |
| **能塞进多少第三方库** | Electron（npm 全量）、PySide6（PyPI + Qt） |
| **未来能否跨到移动端** | **只有 Tauri 2 原生支持** |

下面的排序按「**将来想加原生能力时不被壳挡住**」这一条为主。

### 3.2 候选对比

| 方案 | 壳层语言 | 渲染层 | 扩展性 | 包体 | 主要代价 |
|---|---|---|---|---|---|
| **Electron** | TypeScript（Node） | 自带 Chromium | ★★★★★ **Node 全生态 + 原生模块** | 大（~150MB+） | 体积与内存最大 |
| **Tauri 2** | Rust | 系统 WebView | ★★★★☆ Rust 全量能力 + 官方插件体系（fs / dialog / shell / updater / tray / store / notification / deep-link） | 小（~10MB + Python） | **引入 Rust 工具链**；依赖 WebView2，跨平台渲染有差异 |
| **Wails v3** | Go | 系统 WebView | ★★★★☆ Go 全量能力 | 小 | 引入 Go 工具链；生态明显小于 Tauri |
| **PySide6 + QtWebEngine** | **Python** | 内嵌 Chromium | ★★★★☆ **Qt 全量原生能力**（控件 / 托盘 / 多媒体 / 打印 / WebEngine） | 大（Qt 运行时 ~100MB+） | Qt 授权需合规（LGPL 可用）；打包复杂 |
| **NW.js** | TypeScript（Node） | 自带 Chromium | ★★★★☆ 与 Electron 同类 | 大 | 生态活跃度与资料远低于 Electron |

### 3.3 按场景推荐

| 你的优先级 | 推荐 |
|---|---|
| 扩展性第一、生态最熟、不介意体积 | **Electron** |
| 扩展性强 + 包体小 + 未来可能出移动端 | **Tauri 2** |
| 想与后端**同栈（纯 Python）** | **PySide6 + QtWebEngine** |
| 偏好 Go 生态 | **Wails v3** |

**对本项目的倾向**：**Tauri 2** 或 **Electron**。

- 选 **Tauri 2** 的理由：包体与内存小得多；官方插件体系覆盖我们要的原生能力（文件监听 / 托盘 / 通知 / 更新）；**唯一能延到移动端的选项**；长期产品形态更合适。
- 选 **Electron** 的理由：如果「扩展性」是最硬的约束 —— Node 生态能塞进任何东西，遇到问题资料最多，踩坑成本最低。

**PySide6 的特殊价值**：它是唯一能让**壳与后端同栈**的选项（都是 Python），若你更看重"少一套语言"，它值得认真考虑 —— 代价是 Qt 授权合规与更大的包体。

> 注意：无论选哪个，**真正的难点仍在 Python 侧**（进程生命周期、端口、数据目录，见第二节与第五节），壳的选择不会改变这一点。
### 3.4 平台范围收窄后的重新评估（Windows 桌面）

**前提变了**：本期只要求「**稳定支持 Windows 桌面端**」，且**移动端不做**。

**这直接消掉了 Tauri 2 的两个主要优势：**

| Tauri 的优势 | 在 Windows-only + 无移动端下还成立吗 |
|---|---|
| 包体小（~10MB vs ~150MB） | ⚠️ 成立，但**对单用户本机工具不重要** |
| 唯一能延到移动端 | ❌ **不成立** —— 移动端已排除 |
| Windows 上用 WebView2（即 Chromium） | 原先的"跨平台渲染差异"顾虑消失 —— 对两边都是加分 |

**而 Electron 在这个约束下几乎没有短板：**

| 维度 | Electron |
|---|---|
| 扩展性 | ★★★★★（Node 全生态 + 原生模块） |
| Windows 成熟度 | 最好 —— 坑基本都被踩过，资料最多 |
| **桌面跨平台** | ✅ 仍然支持（Win / macOS / Linux）—— 选它**不牺牲**桌面跨平台性，只牺牲移动端 |
| 壳层语言 | TypeScript —— **与前端同语言**，不必为壳学 Rust / Go |
| 包体 | 大 —— 但本期不敏感 |

### 3.5 选型结论：Electron

**理由**（针对「稳定支持 Windows 桌面端」）：

1. **"稳定"的最强保障是生态** —— Windows 上 Electron 的坑基本都有现成答案；
2. **不必引入第二门语言** —— 壳是 TypeScript，与前端同一套技能；
3. **Windows 打包与分发成熟** —— `electron-builder` 直接出 NSIS 安装包，签名与更新都有现成方案；
4. **保留桌面跨平台的可能** —— 若将来要出 macOS / Linux，Electron 本来就能出；
5. **唯一让掉的是移动端**，而移动端已明确不做。

**诚实说明 Electron 的最大代价**：**sidecar（Python 后端）的进程管理要自己做**。这不像 PySide6 那样能与后端同进程。

但这条**本来就是必须做的**（第二节的难点 #1，以及第五节阻塞项）—— 换成任何非 Python 壳都躲不掉。而且 Electron 这边有成熟模式，落地要点见第十一节。

> **备选**：若"不想引入跨进程复杂度"的权重更高，**PySide6 + QtWebEngine** 是架构最简的选项（壳与后端同栈，可同进程起 uvicorn）。代价是 Qt 授权合规、QWebEngineView 集成细节要摸索、社区资料少于 Electron。
## 四、Web 与桌面的关系

### 4.1 桌面为主（已定）

**决定：核心用桌面端开发。** 触发原因是笔记 —— 要**读取本地笔记，甚至改造本地笔记**。

### 4.2 先澄清：Web 不是「必须把 Markdown 上传到服务器」

这个说法**不准确**。现代浏览器有 **File System Access API**（`showDirectoryPicker()`），可以**直接读写用户选定的本地目录**，不需要上传服务器。

**但 Web 有真实的硬限制**，达不到 Obsidian 那种体验：

| 限制 | 说明 |
|---|---|
| **浏览器兼容性** | 主要是 Chromium 系支持；Firefox / Safari 支持不全或没有 —— 等于**要求用户只能用 Chrome / Edge** |
| **授权会被重置** | 浏览器可能"忘记"目录授权，用户需反复确认 |
| **没有文件系统监听** | 浏览器关掉就不能 watch 目录 —— **用户在别的编辑器改了笔记，应用感知不到** |
| **不能后台索引** | 必须用户主动 pick 一个目录，不能静默扫描或常驻索引 |
| **性能** | 大量小文件的遍历与读写走 JS 层，比原生慢 |

**Obsidian 之所以是那个体验，核心恰恰是「vault 就是一个普通本地目录」**：直接读写、外部编辑立即感知、任意路径。这几条浏览器都做不到。

**所以结论不变，但理由要换**：桌面为主不是因为「Web 要上传服务器」，而是因为**浏览器的本地文件能力达不到我们要的体验**。理由写准了，将来才不会被 File System Access API 反驳。

### 4.3 桌面为主之后，还要不要能力抽象层

| 选择 | 前端写法 | 代价 |
|---|---|---|
| 只做桌面 | 直接调桌面 API | 桌面 API 散落各处；将来要出 Web 版就得补抽象 |
| **保留最小抽象**（推荐） | 一层 `platform.ts` | 多一层间接（成本很低） |

**推荐保留最小抽象，但理由不是「将来可能出 Web 版」**（那是 YAGNI），而是：

1. **可测试性** —— 有这层接口，单测可以注入假文件系统，**不必真开桌面壳就能测笔记读写逻辑**；
2. **收口** —— 桌面 API 集中在一处，不散落到各组件。

### 4.4 Web 版的定位：`dev-web` 分支封存（已定）

**决定：Web 版保留但不维护，迁出为 `dev-web` 分支，历史封存。**

#### 4.4.1 这与我先前「不用分支分平台」的建议不矛盾

两者是**不同的事**，必须区分：

| 场景 | 是否该用分支 | 为什么 |
|---|---|---|
| **两个平台并存维护**（桌面 + Web 都作为产品持续迭代） | ❌ 不该 | 会分裂成两份代码，公共部分每次都要手工对齐 —— 冲突是**慢性的** |
| **把一个平台封存冻结**（Web 不再维护） | ✅ 该 —— `dev-web` | 分支的作用正是**把一个历史状态固定下来**，此后不再合并 |

**区别在「是否还会继续合并」**：并存维护意味着持续的双向合并（分支不适合）；封存意味着**单向冻结、永不合并**（分支 / tag 都适合）。

#### 4.4.2 `dev-web` 分支上有什么

诚实地说：**当前它与主线分出的点内容相同** —— 因为 Web 版从未被产品化（没有部署配置、没有 Dockerfile、没有生产构建流程）。它一直只是 `scripts/dev.py` + `vite dev` 这套开发基础设施。

所以这个分支的意义是**标记一个决策点**（「Web 作为产品形态到此封存」），而不是隔离两套代码。

#### 4.4.3 必须写明的一条

> **`dev-web` 是冻结的历史，不再合并回主线，也不再维护。**

否则它会变成慢性冲突源 —— 将来总有人想问「主线的前端改进要不要同步过去」。**封存的分支必须明确它是死的。**

（若只是要一个不可变的历史标记，`git tag archive/dev-web` 语义更准 —— tag 天然不可移动，而 branch 暗示"还会动"。两者都可以，关键是写明不再合并。）

#### 4.4.4 主线仍然能在浏览器里跑

**「浏览器调试」不是「Web 产品形态」，它不会被封存**：

```text
vite dev + 浏览器      ← 开发调试形态，主线保留（桌面前端也要用它开发）
Web 部署给用户访问      ← 产品形态，封存进 dev-web 分支
```

主线的前端代码本来就是 React + Vite，`npm run dev` 天然在浏览器里跑 —— **这是开发基础设施，与产品形态无关**。

#### 4.4.5 连带简化：不再需要能力降级

| 能力 | 主线（浏览器调试） | 桌面（产品） |
|---|---|---|
| 教材生产 / 学习区 / 书架 | ✅ | ✅ |
| 笔记 vault 直连任意目录 | ❌ 不实现 | ✅ |
| 代码沙盒真实执行 | ⚠️ 浏览器内 | ✅ 子进程 |

不需要为 Web 维护降级路径；`platform.ts` 抽象层的理由回到「可测试性 + 收口」（见 4.3）。
### 4.5 平台差异用代码抽象，不要用分支

一个自然的想法是「fork 两个分支，一个做桌面端、一个做 Web 端」。**不建议**，理由：

| 理由 | 说明 |
|---|---|
| **分支表达「时间分叉」，不表达「长期并存的维度」** | 分支的用途是并行开发、最后合回；而平台差异是**永久并存**的两个维度 |
| **它会把「一份代码」变成「两份代码」** | 与「前端代码保留、一份代码两种形态」直接矛盾；同一处修复要在两个分支各改一遍 |
| **合并冲突会持续产生** | 两边都在改前端，公共部分每次都要手工对齐 —— 冲突不是一次性的，是慢性的 |
| **平台差异本来就适合用代码表达** | 这正是 `platform.ts` 的作用：差异是**运行时的能力判断**，不是仓库的分叉 |

**建议的分支用法：**

| 用途 | 做法 |
|---|---|
| 日常开发 | 一条主线 |
| 单个功能 / 单个任务 | 短生命周期 feature 分支，**做完合回** |
| **桌面化这种大改动** | 也是 feature 分支 —— **临时分叉，最终合回** |
| **平台差异** | 代码里的能力抽象 +（可选）构建配置 |

**两种形态怎么产出**：推荐**运行时探测**（一份产物，运行时按平台标志选用对应 adapter），而不是构建期切换两份产物 —— 本项目差异很小，不值得多一套构建流程。

**唯一的例外**：如果两端功能会**长期分化**（各自有独立功能集），那说明它们是**两个产品**，才值得拆仓库 / 永久分支。按现在的规划，它们是**同一个应用的不同外壳**。
### 4.6 移动端与桌面端：一套还是两套

**先说现状**：`PRD.md` 的非目标明确写着「**不做移动端原生应用**」—— 所以这不是现在要做的决定。下面是"如果有那天"的架构预期。

#### 4.6.1 关键约束：本地 Python 后端在移动端跑不了

| 平台 | 能否跑本地 Python 后端 |
|---|---|
| Windows / macOS / Linux（桌面） | ✅ |
| **iOS** | ❌ 系统不允许 fork/exec 子进程，App Store 政策也不允许 |
| **Android** | ⚠️ 技术上有方案（如 Chaquopy），但限制多、体验差 |

**所以「本地 Python 后端」这个架构在移动端基本不成立。** 移动端只有两条路：**后端上云**，或者**不做**。

#### 4.6.2 一套还是两套：按层回答

| 层 | 能否一套 | 说明 |
|---|---|---|
| **后端逻辑** | ✅ **可以** | 同一个 FastAPI —— 桌面跑本地、移动连云端，只是部署形态不同 |
| **API 契约**（`contracts.ts` 类型） | ✅ **可以** | 类型定义共用，且这正是「Contracts 先行」的收益 |
| **前端 UI** | ❌ **很难** | React DOM 与 React Native 是两套渲染层；Tailwind / DOM API 不能直接用 |
| **壳** | ❌ **两套** | 桌面壳与移动壳是不同产物 |

**结论：既不是"一套"也不是"两套"，而是分层复用** —— 后端逻辑与契约可共用，UI 与壳必须分开。

#### 4.6.3 一个已定的设计正好支撑它

**API 地址运行时注入**（4.1）本来是为了桌面壳的动态端口而提的，但**同一个机制正好支持"指向上云的后端"**。

也就是说：将来要做移动端，**不需要推翻桌面端的设计**。前提是守住一条 —— **后端不要假设「自己总在 localhost」**：

- API 地址：运行时注入（4.1）✅ 已定
- 数据目录：可配置、不绑仓库（5.3）✅ 已定

这两条做到了，上云时的改动面就小。

#### 4.6.4 若真要做移动端，选哪条路

| 方案 | 前端复用 | 后端 | 代价 |
|---|---|---|---|
| **Tauri 2 mobile** | 高（同一份 WebView 前端） | 必须上云 | 需要 Tauri（正好与桌面同壳） |
| **Capacitor** | 高（同一份前端） | 必须上云 | 桥接层生态 |
| **PWA / 移动网页** | **100%** | 必须上云 | 能力受浏览器限制 |
| **React Native** | 低（只共用契约与业务逻辑） | 必须上云 | **UI 要重写** |
| 原生（Swift / Kotlin） | 无 | 必须上云 | 两套 UI + 两套逻辑 |

**推荐 Tauri 2 mobile**（如果那时桌面用的是 Tauri）—— **同一份前端、同一个壳体系**，是复用度最高且不引入第二套工具链的路径。

> 这条也顺带**加强了 Tauri 2 作为桌面壳的权重**：它是唯一能在将来把移动端纳入同一个壳体系的选项（Electron 没有移动端方案）。
## 五、现有代码里的阻塞项（已取证）

这几处**现在就是 Web 应用也不理想**，桌面化只是让它们变成硬阻塞：

| # | 阻塞 | 位置 | 为什么阻塞 |
|---|---|---|---|
| 1 | **项目根靠 `pyproject.toml` 向上定位** | `config/paths.py` | 打包后无此文件 → 启动即 `RuntimeError("未找到项目根")` |
| 2 | **端口硬编码 8000** | `scripts/dev.py`、`frontend/services/runtime/apiClient.ts`、`api/main.py`（CORS 白名单） | 端口冲突；前端不知道后端在哪 |
| 3 | **数据目录在仓库内** | `config/paths.py` 的 `DATA_DIR = PROJECT_ROOT / "data"` | 安装后应写系统标准目录（Windows `%APPDATA%\<App>`） |
| 4 | **API 地址是编译期常量** | `apiClient.ts` | 桌面版端口运行时才定（见 4.1） |
| 5 | **没有单实例控制** | — | SQLite 是 WAL + 连接池，多实例同时开会互相干扰 |

**第 1–4 条与桌面无关也该修** —— 它们是「把仓库当运行目录」的产物，Web 部署同样会踩。属**阶段 0**，不需要引入任何桌面依赖。

## 六、打包 Python：不是必须 PyInstaller

先分清两件事：

| 事项 | 是什么 | 什么时候需要 |
|---|---|---|
| **桌面软件** | 有窗口、双击启动、像应用 | 阶段 1 |
| **打包分发** | 让没有开发环境的机器也能跑 | 阶段 2 |

**只在自己机器上用，根本不需要打包** —— 环境已经在了，壳只要用 `sys.executable` 或 `uv run` 拉起后端即可。**PyInstaller 只在「要分发给别人」时才需要，而且它不是唯一选项。**

| 方案 | 机制 | 优点 | 代价 |
|---|---|---|---|
| **不打包**（拉现有环境） | 壳调用 `uv run` / `sys.executable` | 零打包工作 | 只适合开发机 |
| **uv 管理独立环境** | 分发 `pyproject.toml` + `uv.lock`，首次启动 `uv sync` | **与项目现有工具链一致**；依赖解析可靠 | 目标机器需有 uv；首次启动要联网 |
| **embeddable Python + 依赖目录** | 内置官方 embeddable Python，预装依赖 | 体积与启动可控；不依赖用户环境 | 要自己写启动脚本与离线依赖准备 |
| **PyInstaller** | 分析 import，打成单目录 / 单文件 | 最成熟、生态广、用户零依赖 | 动态导入要写 `hiddenimports`；单文件模式每次启动解压 |
| **Nuitka** | 编译成 C 再打包 | 启动快、可优化 | 编译慢；对部分库兼容性差 |

**这个项目的特殊风险**：后端依赖 **LangChain / LangGraph** —— 这类库大量**动态导入**，正是 PyInstaller 最需要手工补配置的地方。

**建议顺序**：① 阶段 1 不打包；② 要分发时先试 **uv 独立环境**（与现有工具链一致，风险最低）；③ 若必须单文件或零依赖，再上 **PyInstaller**，并预留时间处理动态导入。

（体积与启动速度需要实测，这里不给凭印象的数字。）

## 七、分阶段建议

| 阶段 | 内容 | 需要桌面依赖吗 |
|---|---|---|
| **0 解耦** | ① 数据目录可配置 + 系统标准目录兜底；② 端口可配置 + 动态空闲端口；③ API 地址运行时注入；④ 单实例控制 | ❌ 纯改进 |
| **1 套壳跑通** | 开窗口 → 拉起现有 Python 环境 → 加载前端产物。**不打包** | ✅ 引入壳 |
| **2 打包分发** | 按第六节选方案；先试 uv 独立环境 | ✅ 打包工具 |
| **3 产品化** | 自动更新、安装包、签名、崩溃恢复 | ✅ |

**建议阶段 1 以后暂缓。** 理由：功能还在设计阶段（大纲契约未定稿、画像只有存储、知识地图未投影）。此时套壳会**锁定产品形态**，而功能尚未收敛，之后每次改动都要同时面对「Web 与桌面两套启动路径」。

**但阶段 0 可以顺手做** —— 它不引入桌面依赖，纯粹把「运行目录假设」解耦，对现在与将来的任何部署形态都是净收益。

### 阶段 0 实施结果（已完成）

在 `dev-desktop` 分支上完成，**未引入任何桌面依赖**：

| # | 项 | 实现 |
|---|---|---|
| 1 | **数据目录可配置** | `config/paths.py`：`TEACHERAGENT_DATA_DIR` 显式覆盖 > 开发态 `<项目根>/data` > 系统标准目录（Windows `%LOCALAPPDATA%\TeacherAgent` / macOS `~/Library/Application Support` / Linux `$XDG_DATA_HOME`） |
| 2 | **项目根不再抛异常** | `find_project_root()` 找不到 `pyproject.toml` 时返回 `None`（旧实现抛 `RuntimeError`，打包后启动即失败）；`PROJECT_ROOT` 安装态为 `None` |
| 3 | **`.env` 位置可配置** | `TEACHERAGENT_ENV_FILE` 覆盖 > 项目根 > 数据目录；`config/env.py` 改为**按需读 `paths.ENV_FILE`**（原来是模块级常量绑定，运行期覆盖不生效） |
| 4 | **端口可配置** | `scripts/dev.py` 读 `TEACHERAGENT_PORT`（默认 8000） |
| 5 | **API 地址运行时注入** | `frontend/services/runtime/apiClient.ts`：解析顺序 `window.__TEACHERAGENT_API__`（桌面壳 preload 注入）> `VITE_API_BASE_URL` > 开发默认；**每次请求重新解析**，注入晚于模块加载也能生效 |

**验证**：后端 `pytest` **85 项通过**（含 6 项新增路径契约）；前端 `npm test` **70 项通过**（含 3 项新增地址解析契约）、`lint` 与 `build` 通过。

**过程中发现并修正的一处既有问题**：`config/env.py` 原来是 `from .paths import ENV_FILE`——**模块级常量绑定**，意味着运行时改 `paths.ENV_FILE` 无效。改为按需读取后，`.env` 位置才真正可覆盖。

**关于单实例的修正**：先前写的「SQLite 是 WAL，多实例会互相干扰」**不准确** —— WAL 本身支持多进程（单写多读）。真实风险是**并发迁移**与用户困惑。单实例控制属 Electron 主进程职责（`requestSingleInstanceLock`），留到阶段 1。

## 八、顺带两个真实收益

桌面化不只是「换个窗口」，它解锁两件 Web 做不到的事：

1. **笔记 vault 直连** —— PRD 要把笔记区对标 Obsidian，而浏览器不能任意访问本地目录；桌面版能直接指向 `E:\笔记`。
2. **代码沙盒真实执行** —— 学习区的沙盒现在在浏览器内跑；桌面版可让 Python 后端在受控子进程里真执行。

这两条会**反过来影响功能设计**，所以「要不要桌面化」应当尽早定，即使实现放到后面。

## 九、笔记 vault 的读写与改造

桌面为主是笔记驱动的，而**「改造用户的本地笔记」是危险操作** —— 以 `E:\笔记` 这类多年积累的真实资产为例。这一节先把安全设计摆出来。

### 9.1 三类操作，风险递增

| 操作 | 风险 | 需要什么保护 |
|---|---|---|
| **只读索引**（扫描目录、建全文索引、双链分析） | 低 | 只读授权 |
| **单条改写**（用户在应用内编辑一篇笔记） | 中 | 写入前备份 + **冲突检测**（文件在外部被改过吗） |
| **批量改造**（重命名、加元数据、批量迁移/重排） | **高** | **预览 diff → 确认 → 应用 → 可撤销** |

### 9.2 复用已有机制：暂存 → 确认 → 应用

批量改造**不应直接写文件**，而应复用我们已经在知识图上定过的模式：

```text
产出改动（agent 或 user） → 暂存（预览 diff） → 人确认 → 应用到文件 → 可撤销
```

这与知识点的「暂存 → commit」、领域演化的「预览 diff → 应用」是**同一个模式** —— 设计上保持一致，不另造一套。

### 9.3 vault 的边界（待定）

| 项 | 选项 |
|---|---|
| vault 位置 | 用户指定任意目录（像 Obsidian）/ 固定应用数据目录 |
| 外部改动感知 | 需要文件系统监听（桌面能力） |
| 元数据写哪 | 写进笔记文件（frontmatter）/ 存在应用数据库 |
| 是否允许重命名 / 移动 | 高风险，需明确规则与引用更新策略 |

### 9.4 一条硬原则

> **应用绝不静默改写用户的笔记文件。**

任何写入都要满足三条：① **有明确触发**（用户操作，或用户已确认的 agent 建议）；② **可追溯**（记下改了什么）；③ **可撤销**。

## 十、Electron 落地要点（Windows）

选型定稿前的预研，**不是实施计划**。

| 事项 | 做法 |
|---|---|
| **单实例** | `app.requestSingleInstanceLock()` —— 避免多实例同时开 SQLite |
| **拉起后端** | `child_process.spawn` 启动 Python；轮询 `/health` 确认就绪；退出时 kill 子进程 |
| **端口** | 启动时取空闲端口 → 经启动参数 / 环境变量传给 Python → 再注入渲染进程 |
| **API 地址注入** | 用 `webPreferences.additionalArguments` 或 preload 暴露给前端（对应 4.1） |
| **数据目录** | `app.getPath('userData')` → 以环境变量传给后端（对应 5.3） |
| **开发模式** | 主进程加载 `http://localhost:5173`（vite dev），DevTools 直接调试 |
| **生产模式** | 加载打包后的 `dist/index.html`（注意 `file://` 与相对路径） |
| **打包** | `electron-builder` → NSIS 安装包（可另出 portable） |
| **签名** | 可选；不签会在 SmartScreen 提示「未知发布者」，自用可接受 |
| **更新** | `electron-updater`（可选，阶段 3） |

### 三个最容易出问题的地方（提前知道能省时间）

1. **后端启动时序** —— 渲染进程可能在 `/health` 就绪前就发请求。
   做法：**先等健康检查通过，再 `loadURL`**。
2. **僵尸进程** —— 主进程被强杀时子进程可能残留。
   做法：监听 `before-quit` / `will-quit` 主动 kill；并让后端在父进程消失时自杀（如检测 stdin 关闭）。
3. **`file://` 加载前端** —— 前端资源路径与路由要相对化，否则**打包后白屏**（这是 Electron 最常见的坑）。
